# Project DOTTO 벤치마킹 및 AUTO-ONE 적용 검토

- 검토일: 2026-11-18
- 참고 저장소: https://github.com/2dowon/Project-DOTTO
- 대상 저장소: https://github.com/ehdrlf2797-create/AUTO-ONE
- 기준: 참고 저장소의 공개 소스와 현재 AUTO-ONE 저장소 상태를 읽어 검토
- 상태: 기술 검토 문서. 애플리케이션 코드 변경 및 로또 기능 구현은 아직 수행하지 않음

## 1. 검토 요약

Project DOTTO는 2020년에 작성된 Python 3.8/3.9, Jupyter Notebook, Flask 기반의 로또 데이터 분석·번호 생성 프로젝트다. README는 1회부터 936회까지의 당첨 이력을 분석하고, 출현 빈도가 높은 상위 10개 번호 중 6개를 무작위 추출하는 방식을 설명한다. 시각화와 1등 당첨 판매점 지도도 포함한다.

벤치마킹할 제품 기능은 다음과 같다.

1. 일반 무작위 번호 생성
2. 과거 출현 빈도 기반의 탐색용 번호 생성
3. 사용자가 일부 번호를 지정하는 반자동 생성
4. 회차별 당첨 이력과 번호 통계 시각화
5. 당첨 판매점 위치 지도

단, 과거 출현 빈도는 미래 추첨 결과를 예측하지 못한다. 모든 유효한 6개 번호 조합은 동일한 당첨 확률을 가진다는 점을 사용자 인터페이스와 분석 설명에 명확히 표시해야 한다. '예측', '당첨 보장', '확률 상승'으로 오해할 표현은 사용하지 않는다.

## 2. DOTTO 소스에서 확인한 개선점

### 2.1 데이터 수집 노트북

대상: `lotto_data_crawling.ipynb`

확인 사항:
- 회차 범위가 `range(1, 937)`로 고정되어 있어 936회 이후의 결과를 자동으로 포함하지 않는다.
- 회차마다 `requests.get(url)`을 실행하지만 timeout, HTTP 상태 코드, 재시도 처리가 없다.
- 응답에서 당첨번호 요소를 찾지 못해도 빈 목록이 누적될 수 있어 부분 실패가 정상 데이터처럼 취급될 수 있다.
- 번호별 횟수를 세기 위해 전체 목록을 1~45에 대해 반복 검색한다. `collections.Counter` 한 번으로 계산하는 편이 간결하고 효율적이다.
- 오래된 HTML 화면 구조에 직접 의존한다. 공식 제공 데이터 또는 공식 결과 응답을 우선하고, 파싱 실패 시 데이터 갱신을 실패 처리해야 한다.
- 수집 완료를 판단할 때 마지막 회차 번호, 추첨일, 번호 6개, 보너스 번호를 검증해야 한다.

권장 개선:
- 공식 동행복권 자료를 데이터 공급원의 최우선으로 지정한다.
- 최신 회차는 추정하지 말고 실제 게시된 결과에서 확인한다.
- timeout, 제한된 재시도와 지수형 backoff, 요청 간격, 오류 로그를 둔다.
- 회차별 원본 응답과 정규화 결과를 분리하고, 성공적으로 검증된 데이터만 저장한다.
- 이전에 수집한 회차는 캐시하고 새 회차만 증분 갱신한다.
- 고유 제약조건 `round` 및 데이터 검증으로 중복·누락을 감지한다.

### 2.2 데이터 기반 번호 생성 노트북

대상: `lotto_program.ipynb`, `lotto_data_crawling.ipynb`

확인 사항:
- 상위 10개 번호 목록이 코드에 상수로 고정되어 있다.
- `if top10_lotto in lotto_num == True`는 의도한 비교가 아니다. Python의 비교 연쇄로 해석되므로 과거 당첨 조합 검사 로직으로 사용할 수 없다.
- 반자동 생성 코드의 `if select_lotto in top10_lotto != True:`도 중복 검사를 의도대로 수행하지 않는다.
- 수동 번호 개수의 범위(0~6), 번호 범위(1~45), 중복, 숫자 이외 입력을 충분히 검증하지 않는다.
- 사용자 입력 변수와 생성 번호 변수를 재사용해 로직을 읽기 어렵게 만든다.
- 상위 10개만 뽑아 그중 6개를 선택하는 방식은 과거 통계를 시각화하는 탐색 기능일 뿐 미래 당첨을 예측하는 방법이 아니다.

권장 개선:
- 번호 생성기, 입력 검증, 빈도 계산을 UI와 분리된 순수 함수로 구현한다.
- 기본 생성 방식은 1~45에서 중복 없이 균등 무작위 추출로 둔다.
- 빈도 가중 생성은 사용자가 선택하는 별도 실험 모드로 제공하고, 통계적 예측이나 확률 우위가 아님을 표시한다.
- 반자동 생성은 선택 번호의 범위와 중복을 먼저 검증한 후 남은 번호만 추출한다.
- 생성 결과는 항상 오름차순 6개로 정규화한다.
- 테스트에서 재현할 수 있도록 난수 생성기 또는 seed 주입을 지원한다.

### 2.3 Flask 웹 애플리케이션

대상: `flask/app.py`

확인 사항:
- 두 생성 함수 모두 `/` 경로를 등록하고 있다. 홈 경로의 매핑이 모호해질 수 있다.
- 생성 동작이 페이지 경로와 결합되어 있고 입력 오류에 대한 응답 규약이 없다.
- 개발 서버 실행 설정 외에 배포용 서버 설정, 환경 설정, 테스트 구성이 확인되지 않는다.

권장 개선:
- `/`는 홈 화면 전용으로 두고 생성은 별도 POST API로 분리한다.
- 예: `POST /api/lotto/generate`, `GET /api/lotto/statistics`, `GET /api/draws/latest`.
- 입력 오류는 일관된 400 응답, 외부 데이터 공급원 오류는 503 등으로 구분한다.
- 디버그 모드는 개발 환경에서만 켜고, 운영은 WSGI 서버와 환경 변수 기반 설정을 사용한다.
- API 입출력 스키마와 헬스 체크를 추가한다.

### 2.4 데이터 시각화

대상: `lotto_data_visualize.ipynb`, `lotto_excel.xlsx`

확인 사항:
- 엑셀 데이터는 2020년 11월 무렵 936회까지의 과거 자료를 보여준다.
- `Unnamed` 열과 다단 헤더 등 원본 정리 과정이 필요한 형태가 확인된다.
- 최신 데이터가 추가될 때 시각화와 통계 자료가 함께 갱신되는 구조가 확인되지 않는다.

권장 개선:
- 회차, 추첨일, 당첨번호 6개, 보너스 번호, 등위별 당첨자·당첨금 등 명확한 스키마로 정규화한다.
- 번호별 누적/기간별 출현 횟수, 홀짝, 구간 분포, 연속 번호, 번호 쌍/삼중항을 구분해 보여준다.
- 최근 10/30/50회 통계는 기간을 명시하고 전체 누적 통계와 혼동하지 않게 한다.
- 표본 수와 마지막 갱신 회차·시각을 항상 표시한다.
- 단순 빈도 차트를 예측 신호처럼 해석하지 않도록 안내 문구를 둔다.

### 2.5 판매점 지도

대상: `lotto_strore_map.ipynb`, `flask/templates/lotto_store.html`

확인 사항:
- 지도와 좌표가 정적 HTML에 포함되어 있어 판매점 주소나 당첨 이력 변경 시 재생성이 필요하다.
- 지도 템플릿은 오래된 CDN 버전과 여러 외부 스크립트에 의존한다.
- 파일명 오탈자(`strore`) 등 유지보수성이 낮은 부분이 있다.
- README의 '수도권' 설명과 노트북에 보이는 전국 주소 예시가 일치하지 않는다.

권장 개선:
- 판매점, 주소, 좌표, 당첨 회차, 데이터 출처, 확인 시각을 별도 테이블로 관리한다.
- 지도에는 데이터 기준일과 주소/좌표 검증 상태를 표시한다.
- 지오코딩은 캐시하고 요청 제한을 준수한다.
- 지역·회차·당첨 등수 필터를 지원하고, 좌표 누락 건은 목록으로 제공한다.
- 외부 지도 라이브러리는 지원되는 안정 버전으로 고정하고 보안 업데이트를 관리한다.

## 3. AUTO-ONE 적용 원칙

검토 당시 AUTO-ONE의 기본 브랜치 `main`에는 `README.md`만 존재한다. 애플리케이션 코드, 의존성 잠금 파일, 테스트, CI 설정은 아직 확인되지 않았다. 따라서 현재 시점에는 실제 버그 수정이나 성능 개선을 적용할 기존 코드는 없다.

로또 분석을 AUTO-ONE에 포함하기로 결정한다면 일반 자동화 코어와 분리된 선택형 모듈로 설계한다.

권장 경계:
- `modules/lotto/domain`: 회차·번호 검증, 통계 계산, 조합 생성
- `modules/lotto/providers`: 공식 결과 데이터 수집과 정규화
- `modules/lotto/storage`: 회차·판매점 데이터 저장 및 캐시
- `modules/lotto/api`: 결과 조회·통계·생성 API
- `modules/lotto/ui`: 번호 생성 화면, 분석 대시보드, 판매점 지도
- `tests/lotto`: 도메인·공급원·API 테스트

다만 AUTO-ONE의 핵심 목적이 통합형 PC/웹 자동화 시스템인 만큼, 로또 모듈을 핵심 자동화 런타임과 강하게 결합하지 않는다. 독립적으로 켜고 끌 수 있는 기능으로 유지한다.

## 4. 단계별 구현 및 검증 계획

| 단계 | 작업 | 완료 기준 |
|---|---|---|
| 0 | 앱 기술 스택과 배포 환경 확정 | 런타임, 저장소, 로컬 실행 절차 문서화 |
| 1 | 공식 당첨 데이터 공급원 구현 | 최신 회차 검증, 실패 시 오래된 결과를 최신으로 표시하지 않음 |
| 2 | 데이터 모델과 무결성 검사 | 회차 중복·누락, 번호 범위·중복·보너스 검증 테스트 통과 |
| 3 | 통계 분석 엔진 | Counter 기반 통계와 기간별 통계의 단위 테스트 통과 |
| 4 | 균등·가중·반자동 생성 | 6개·고유·1~45 범위, 사용자 입력 검증 테스트 통과 |
| 5 | 대시보드와 판매점 지도 | 데이터 기준 회차와 갱신 시각 노출 |
| 6 | 최적화·배포 | 캐시/인덱스 측정, CI 통과, 운영 설정·오류 모니터링 확인 |

필수 테스트 사례:
- 번호 배열은 정확히 6개이며 모두 정수 1~45이고 중복이 없다.
- 보너스 번호는 본번호 6개와 겹치지 않는다.
- 수동 지정 번호가 0~6개인 경우 각각 정상 동작한다.
- 범위 밖 번호, 중복 번호, 문자열 입력은 거부한다.
- 공식 자료 응답이 누락되거나 형식이 바뀌면 해당 회차를 저장하지 않는다.
- 최신 회차 조회는 실제 공식 게시 결과가 없을 때 이전 회차를 최신으로 둔갑시키지 않는다.
- 같은 데이터를 재수집해도 중복 회차가 생성되지 않는다.
